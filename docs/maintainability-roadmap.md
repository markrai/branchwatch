# BranchWatch maintainability roadmap

Source baseline: d0c542e10debdc212123824f0c7c4588fa49190d. Preserve guarded native operations, one-shot alarm behavior, snapshot formats, user-visible workflows and fail-closed browser gates. Prefer narrow changes, explicit state ownership and testable services to a framework rewrite.

| Phase | Scope |

| R.1 | Sticky-note interaction coordination |
| R.2 | Passive body and native-window lifecycle |

## R.0

The sticky-note controller previously saved before closing windows, although closing can commit an unfinished title edit. Capture pending titles, geometry and due alarm state before closing, suppress ordinary close-state transitions during application disposal, then perform the final save after close callbacks. Retain the established session-ending disposal path: WPF can close windows before OnExit, so deferring disposal would risk ordinary close callbacks marking notes closed during shutdown. A shutdown cancelled externally after the notification remains an unqualified lifecycle scenario, not a resolved defect. Start is idempotent and cannot revive a disposed controller. A minimal native desktop interface permits exercising the actual controller and WPF windows without requiring virtual desktop COM support in CI.

Tests cover unfinished rename on shutdown, cancelled rename and dismissed alarm, ordinary close versus shutdown, and duplicate start/disposal. Windows CI rejects warnings in the solution test build. Existing browser, packaging and evidence checks remain unchanged. Physical session-ending/cancellation, desktop affinity, focus and native click-through still require real Windows acceptance. Disk-write failure handling remains best-effort at exit; no guaranteed persistence is claimed when storage is unavailable.

Later phases should preserve the current user-facing behavior and not unlock unqualified Firefox operations or native browser placement.

## R.1

StickyNoteInteraction owns temporary editing transitions, the rename baseline, alarm dialog reentry and closing guards. It delegates the existing five-second preview state to StickyNoteTemporaryEditing and operates on the existing per-note model. Header acknowledgement takes precedence over temporary editing, including for collapsed notes. All time-dependent decisions take explicit timestamps. The WPF window translates the returned transitions into focus, timer, hook and presentation effects; it no longer owns a second copy of these interaction flags or the rename comparison. No new serialized state is introduced. While a rename or alarm dialog is active, new temporary edit sessions are rejected, and new rename/dialog actions are rejected during closing. Closing still permits committing an already-started rename. Existing window geometry, passive-body/native ownership, modal dialog implementation, controller persistence and alarm scheduling remain unchanged. R.2 owns native lifecycle extraction.

Pure interaction regression tests cover the preview deadline, held editing, alarm priority, collapse/opaque guards, rename commit/cancel/reset, dialog reentry and closing. Existing STA tests retain their window-level assertions; physical focus, mouse, native click-through and timing remain unqualified.

The alarm dialog now explicitly commits an active title edit before showing, instead of relying solely on the subsequent WPF deactivation event. This is a defensive ordering change preserving the established focus-loss commit semantics. Six pure tests and one WPF combined alarm/editing regression were added. No line-count target: the window still owns native presentation effects, which are the subject of R.2.

## R.2

StickyNotePassiveBodyLifecycle owns creation, attachment, alignment, reentry, failure suppression, removal and disposal of the auxiliary click-through body. The window supplies eligibility and layout readiness, handles editing on desktop changes, and renders the owner when attachment changes. A small disposable body interface allows lifecycle testing without Win32. The existing native adapter still owns the HWND, WPF body, styles, pixel bounds and alarm animation. Native ownership and current-desktop checks are retained, including a fresh affinity check before changed native placement. A failed show or alignment leaves the owner presentation in place and suppresses repeated creation until an explicit transparency change or expansion resets the failure. An affinity loss observed during refresh or failed alignment detaches the body without latching failure; the next eligible refresh can recreate it. A failed candidate is disposed before failure notification. Closing is terminal and does not render the closing owner. A candidate invalidated by a reentrant removal or shutdown cannot attach later. No persistent data, settings, alarm deadlines, transparency levels or native style flags change.

Eight pure lifecycle regression tests cover verified owner/layout gating, reuse, show failure, alignment failure, affinity/eligibility loss, reentrant removal, close during creation, exception cleanup and idempotent disposal. Existing WPF interaction and persistence regressions remain. The window code-behind is approximately 717 lines (802 before R.2). The new tests use fake bodies; real HWND styles, multi-monitor alignment, mixed DPI, desktop switches, collapse/expand and alarm outlines still require physical Windows testing. This slice does not replace the native desktop manager or outside-click hook; the hook remains owned by the UI effect dispatcher.

## R.3

DesktopMemoryCaptureService owns capture/probe and transient browser token correlation, plus the existing native re-verification predicate before import. DesktopMemoryDraft owns the unsaved snapshot, transient tokens and browser tab review; folder updates and browser imports require the exact expected draft reference. It validates draft changes and saves the reviewed projection through the existing encrypted store, clearing the draft only after successful persistence. Browser selections synchronize on model changes, not WPF rendering. The shared DesktopMemorySta helper eliminates duplicate STA thread startup logic. The page retains selection/visibility checks, user confirmations, status text, ticket ownership, and restore orchestration for R.4/R.5. No new permission, schema, or browser family is enabled. Stopping the page clears transient draft state; hiding the page retains the draft as before. A stale folder dialog cannot edit a replaced draft. Native and browser qualification remains required.

Seven regressions exercise unique capture correlation, ambiguous/reused identity rejection during re-verification, inspection failure, Firefox lock, stale folder/browser operations, recapture selection reset, failed-save retention and successful reviewed persistence. The page invalidates an in-flight browser import when capture authorization is cancelled (including hide/selection/stop), even if visibility later returns. Confirmed saves recheck the draft reference and selected desktop. The existing optimistic store guard and native checks remain in effect; the native observation is still not atomic with later browser actions. Physical qualification remains outstanding. The page is approximately 907 lines, down from 979. R.4 extracts restore coordination next.

## R.4

DesktopRestoreSession owns one restore attempt, including a copied selection, fresh saved-snapshot verification before preparation and execution, the existing placement/launch services, cancellation, stage transitions and synchronized progress. The page still owns preview rendering, checkbox selection, confirmation and UI dispatch. It cannot execute a preparation from a different session or execute twice; confirmation is represented by the page invoking ExecuteApproved only after the user accepts the prepared list. Both phases run through DesktopMemorySta. The worker reports final per-window outcomes (provisional missing-window results are suppressed for launch candidates); queued UI progress is ignored after execution ends or the page stops. Cancellation on hide, selection change, stop or explicit cancel is cooperative and does not roll back already-issued moves or launches. Disposal occurs after the active worker returns. The cancellation message distinguishes pre-execution cancellation from possible partial execution. No native authorization, matching, placement, launch policy, storage format or browser permission changes.

Six integrated session regressions exercise side-effect-free preparation, single-use approval, launch opt-in, immutable selection, cancellation before preparation/execution and after a move, saved-snapshot drift, foreign approvals and observer failure. Existing matching and launch tests still cover native identity and policy. The settings page is approximately 881 lines (906 before R.4); the remaining preview and presentation state stays in the page. Session methods are intended for one active STA worker at a time, with cancellation from the UI; callers must await that worker before disposal. Tests use synthetic environments rather than physical Win32 operations. R.5 addresses browser authorization next.

## R.5

BrowserAuthorizationSession owns page-scoped capture tickets, consumed import approvals, cancellation revisions and restore approval state. Capture remains tied to the exact draft reference and browser window; attaching requires fresh active desktop and the existing native re-verification before confirmation. Restore uses a shared saved-session predicate both before arming and at redemption. BrowserAuthorizationPolicy centralizes the two-minute monotonic lifetime, eligible native identity predicate and saved restore eligibility. Capture correlation still compares original bounds, handle, process, path, class and title. Re-verification still requires the captured process creation identity and unique normal current-desktop Chromium window. Additional consistency checks require visibility and agreement between native token and observed handle/PID. Firefox remains diagnostic-only.

Restore queue verification runs outside the queue lock; after verification it must reacquire the lock and recheck the exact pending approval, identity, expiry and issued ledger. Cancelling or replacing the approval during verification prevents URL issuance. No wire versions, permissions, snapshot formats or host registration changes. Same-user IPC is not an independent authentication boundary, and native/browser observation remains non-atomic. Physical qualification is still required.

Eight additional regressions cover native handle/PID/visibility mismatch, capture expiry, cancelled and stale imports, stale restore confirmation and saved-session change, cancellation while redemption verifies, replacement while verification is running, and expiry or verification failure during redemption. The page remains responsible for the explicit user confirmation and STA native re-verification; the extracted session owns the lifetime of the approval, not the actual browser process. Settings page is approximately 871 lines, down from 881 before R.5. Native browser placement and live Firefox operations remain blocked.

## R.6

TrayMenuState projects current repository/settings/activity state into labels, tooltips, visibility and enabled states without WinForms; note menu rows contain stable IDs, not captured note objects. TrayMenu owns WinForms menu construction, glyphs, dynamic rows and disposal. TrayService remains the application command coordinator and deferred dispatcher, resolving note IDs at execution time and rejecting deferred callbacks after disposal. SettingsWindowHost owns the single settings window and navigation/activation lifecycle, while the existing pages retain their drafts and refresh semantics. GitOverlayVisibility shares save-and-rollback behavior between tray and settings. Menu order, labels, commands, existing startup registry policy, note placement and desktop-memory authorization are unchanged; dynamic ampersands are escaped for WinForms display. This slice does not change the settings storage format or general persistence strategy.

Six regressions cover pinned/workspace projections, status precedence and truncation, stable note labels/identity, shared overlay save rollback, WinForms menu command routing and dynamic row disposal, and WPF settings-host reuse/disposal. The tray service is approximately 381 lines (571 before R.6). Actual notification-area interaction, focus, desktop affinity and Windows startup registry behavior remain physical checks. Deferred callbacks and deleted-note resolution are guarded in the command coordinator; physical dispatcher timing is not claimed qualified. R.7 addresses refresh work and repeated test infrastructure.

## R.7

UiRefreshCoordinator owns the pending repository/session-driven tray refresh, not repository state or native operations. Notifications from any thread mark the current state dirty and queue at most one dispatcher callback. Explicit commands still render synchronously on the UI thread and consume already-pending work; a subsequent notification is not lost when a callback is already queued. Requests during rendering schedule a follow-up pass. Disposal rejects new work and makes queued work inert before tray resources are released. The render reads current state rather than event payloads. Dispatcher posting is asynchronous; rendering, immediate refresh and disposal remain UI-thread operations. No repository watcher timing, polling, overlay visibility, settings persistence, startup registry, alarm deadlines or native authorization policy changes.

Six coordinator regressions cover event bursts, immediate refresh and later notifications, requests during rendering, disposal, post failure retry and concurrent requests. Shared StaTest.Run preserves original exception stack traces and the existing synchronous STA execution model; StaTest.WithTemporaryDirectory centralizes cleanup, including the settings navigation test that previously left its temporary directory behind. Eight existing STA test bodies or fixtures in four test files now use these helpers without changing their assertions. No production worker or message-pump policy changes. Actual dispatcher timing, notification-area behavior and mixed-desktop/native window interactions still require Windows acceptance. R.8 is the final architectural review and regression qualification phase.

## R.8

The [architecture review and regression qualification record](maintainability-qualification.md) audits the extracted ownership boundaries and captures the actual passing R.7 CI baseline. R.8 closes a remaining modal-confirmation lifecycle gap: DesktopMemoryConfirmation rejects stale or nested approvals; hide, stop, selection change and snapshot reload invalidate an outstanding prompt. The settings page checks visibility, selected and observed active desktop, exact draft and saved snapshot identity, busy and storage state before and after the prompt. Save and delete retain expected-capture persistence checks; restore retains cancellation and native authorization. Four focused tests cover the pure confirmation policy.

R.8 Windows CI and physical acceptance are pending at PR creation. No schema, version, dependency or feature expansion. The qualification record contains a physical checklist and links to the existing Desktop Memory and Firefox procedures. Source-level completion is distinct from interactive release qualification; no case is marked passed without evidence.
